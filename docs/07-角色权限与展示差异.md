# 07 · 角色切换后的权限与展示差异

> 本文档是 `assets/js/01-config.js` 中 `PERM` / `PERM_NOTE` / `VIEW` / `HOME` / `CREATE` 五张表的说明书。
>
> **核心原则：切换角色不改变任何一条数据，只改变四件事——看得见什么、默认怎么排、默认筛什么、能不能改。**

---

## 一、两个角色的定义

| | 产品总监 | 项目经理 |
|---|---|---|
| `role` key | `director` | `pm` |
| 姓名 / 职位 | 「我」· 产品总监 | 「我」· 项目经理 |
| 口号（首页副标题） | 多产品线全局视角 · 规划、节奏、经营与风险 | 单项目执行视角 · 计划、任务、风险与交付 |
| 数据口径 `scope` | `line`（产品线） | `project`（单项目） |
| 顶栏选择器 | 产品线下拉（你建了几条就是几条） | 项目下拉（你建了几个就是几个） |
| 强调色 `--c-accent` | 靛蓝 `#4f46e5` | 青 `#0e7490` |
| 可见模块数 | 14 | 17 |
| 侧栏分组 | 上手与数据 + 公共模块 + 产品总监 | 上手与数据 + 公共模块 + 项目经理 |

> **姓名不是写死的。** `C.ROLES[*].user.name` 里只放占位值 `'我'`，你的真名存在本地库 `DB.me.name`（在「上手与数据 → 上手引导 → 组织与我」里填），`03-store.js` 启动时由 `S.applyMe()` 回填进两个角色对象。改名时 `S.setOrg()` 会顺带把历史记录里 `owner / pm / assignee / reporter / actor / creator / approver / host / sponsor` 上完全等于旧名字的值一起换掉，避免负责人挂在一个不存在的名字上。组织名 `C.ORG` 同理，默认「我的组织」。

角色状态存于 `S.state.role`，持久化到 `localStorage['pmw.role']`；切换时触发 `S.emit('role')`，`06-shell.js` 的订阅者自动调 `Shell.route()` 重渲染当前页。

## 二、四态权限模型

| 态 | 侧栏 | 页面 | 新建/编辑按钮 | 直接输入路由 |
|---|---|---|---|---|
| `full` | 渲染 | 完整 | 高亮可点 | 正常进入 |
| `limited` | 渲染 | 完整 + 顶部说明条 | 可编辑，但**受限字段以只读形态呈现并标注归属**；受限批量动作整条不出现 | 正常进入 |
| `scoped` | 渲染 | 完整 + 顶部说明条 | 全部不出现 | 正常进入（只读） |
| `none` | **不渲染** | — | — | 渲染「无权限」说明页 |

判定入口：

```js
C.permOf(modKey, role)   // 返回四态之一，未在 PERM 中列出的模块默认 'full'
C.canEdit(modKey, role)  // full || limited —— 「能不能进编辑态」
C.canSee(modKey, role)   // 基于 NAV 分组的 roles 字段
```

页面内统一用两个判定，**任何页面都不得硬编码 `role === 'director'` 之类的判断**：

| helper | 含义 | 用途 |
|---|---|---|
| `P.ed(mod)` | `canEdit` = `full \|\| limited` | 是否渲染编辑入口（编辑按钮、批量动作区、拖拽） |
| `P.full(mod)` | `permOf === 'full'` | 是否放开**受限字段与受限批量动作**（`limited` 与 `full` 的实际分界） |
| `P.permTip(mod)` | — | 渲染顶部说明条（文案取自 `C.PERM_NOTE`） |

> `limited` 的受限字段不采用 HTML `disabled`，而是渲染为 `UI.form` 的 `type:'static'`——不产生表单控件、不参与 `UI.readForm` 取值，因此提交时由页面显式回落到原值（`11-requirements.js` 的 `pack(d, base)`、`12-releases.js` 的 `g(k)`）。这样既不会被前端改值绕过，也不会因 `disabled` 控件不提交而把字段清空。

| 团队管理 `team` | full | **none** |

### 3.3 项目经理独占（7 个）

| 模块 | 总监 | PM |
|---|---|---|
| 项目计划 `plan` | **none** | full |
| 任务管理 `tasks` | **none** | full |
| 进度跟踪 `progress` | **none** | full |

| 交付管理 `delivery` | **none** | full |

> **为什么是 `none` 而不是只读？** 总监需要的执行面结论已经通过「仪表盘 / 风险预警 / 项目协同 / 数据分析」四个公共模块以聚合口径呈现——他要知道"项目 P03 落后 8 个百分点、有 2 项高危风险"，而不是"任务 T0142 延期 3 天"。把 7 个执行工具塞进总监侧栏只会稀释决策注意力，还会制造"总监能看但改不了"的尴尬对话。反向同理：PM 看不到产品线预算与团队编制，是组织边界而非技术限制。

### 3.4 三处跨角色受限的具体含义（`C.PERM_NOTE`）

这四条文案会直接渲染在对应页面顶部的说明条里：

| 键 | 文案 |
|---|---|
| `requirements.pm` | 项目经理可查看与推进需求状态，但调整优先级、关闭 / 驳回需求、指派目标版本均需通过「需求变更」走审批。 |
| `requirements.director` | 产品总监可直接调整优先级、状态与版本归属。 |
| `releases.pm` | 项目经理可维护本项目的版本进度、缺陷与阻塞并推进状态；版本类型、归属与四个窗口日期（开发启动 / 需求冻结 / 提测 / 计划上线）由产品总监排期。 |
| `analytics.pm` | 漏斗与留存已收敛到当前项目关联的版本与需求；核心指标按当前项目所属产品线口径展示，ARR / MAU / 续约率等经营指标仅产品总监可见。 |

这三个受限点构成了两个角色之间**唯一的三条协作边界**：

```
需求优先级   ── 总监定，PM 提变更 ──> 需求变更模块走审批
版本上线窗口 ── 总监定，PM 报进度 ──> 版本计划页只读关键日期字段
经营级指标   ── 总监独享，PM 看项目级 ──> analytics 维度自动降级
```

#### 这三条边界在代码里的落点

| 边界 | PM（`limited` / `scoped`）实际看到的 | 代码位置 |
|---|---|---|
| 需求优先级 | 编辑抽屉里「优先级」渲染为只读标签 + *"如需调整请提交「需求变更」走审批"*；提交时回落原值 | `11-requirements.js` `fields()` / `pack(d, base)` |
| 需求关闭 / 驳回 | 状态下拉不含 `已关闭` / `已驳回`（若需求当前已处于该状态则保留该项，避免保存时被静默改写） | `11-requirements.js` `stOpts(cur)` |
| 需求批量动作 | 只有「批量流转状态 / 批量提交变更申请 / 批量导出」；**没有**「批量调整优先级」「批量指派版本」 | `11-requirements.js` `bulkActions()` |
| 新建需求 | 优先级字段标题变为「建议优先级」，带 *"最终优先级由产品总监评审时确认"* | `99-app.js` `req.new` |
| 版本上线窗口 | 开发启动 / 需求冻结 / 提测 / 计划上线四个日期渲染为只读 + *"总监排期"*；版本类型与产品线 / 项目归属同样只读 | `12-releases.js` `dateField()` / `edit()` |
| 版本批量动作 | 「批量顺延上线日」整条不出现（只剩批量调整状态与批量导出说明） | `12-releases.js` `bulkActions()` |
| 经营级指标 | `analytics` 为 `scoped`，`P.ed` 直接为 false，全页无任何编辑入口 | `C.PERM.analytics` |
| 指标集合收敛 | 指标从 `BIZ_KEYS`（ARR / MAU / 续约率 / NPS / 工单量 / SLA）收敛为 `PM_KEYS`（NPS / 工单量 / SLA）——ARR / MAU / 续约率三项经营指标 PM 完全不可见 | `13-analytics.js` `scoped()` / `keys()` |
| 指标口径收敛 | 产品线选择器不渲染；口径固定为**当前项目所属产品线**（指标序列只按 `lineId` 分桶，无项目级序列，这是数据模型下最贴近本项目的口径） | `13-analytics.js` `curLineId()` |
| 分析维度降级 | 趋势分析的「按产品线」维度对 PM 自动降级为「按版本」 | `13-analytics.js` `trend()` |

## 四、默认视图差异（`C.VIEW`）

权限决定"能不能看"，`C.VIEW` 决定"默认怎么看"。同一个页面、同一份数据，两个角色打开时的初始状态不同：

| 模块 | 总监默认 | PM 默认 |
|---|---|---|
| **需求管理** | 按**业务价值降序**<br>额外列：产品线 / 业务价值 / ROI<br>*"按业务价值降序，突出高价值需求"* | 按**交付时间升序**<br>额外列：目标版本 / 负责人 / 进度<br>*"按交付时间升序，突出本项目待办"* |
| **版本管理** | 按计划上线日升序<br>额外列：产品线 / 版本范围<br>*"关注版本节奏"* | 按计划上线日升序<br>额外列：进度 / 阻塞<br>*"突出进度与阻塞"* |
| **风险预警** | 按**等级**排序<br>**预置筛选 `level='高'`**<br>额外列：产品线 / 影响面<br>*"默认只看高等级风险"* | 按**处理时限**排序<br>无预置筛选（全等级可见）<br>额外列：负责人 / 应对措施<br>*"按处理时限排序，全等级可见"* |
| **会议纪要** | 按日期倒序<br>额外列：**决策项数**<br>*"突出决策项"* | 按日期倒序<br>额外列：**Action Item**<br>*"突出 Action Item"* |
| **数据分析** | 维度 = **产品线** | 维度 = **版本** |
| **工作留痕** | *"关注规划调整与版本发布"* | *"关注任务流转与交付验收"* |
| **待办中心** | 按**优先级**排序 | 按**截止时间**排序 |

斜体为 `C.VIEW[role][mod].note`，会渲染在页面视图条上，让用户知道"为什么默认是这个顺序"，并可一键改回。

**关键设计**：默认视图**只是默认**。PM 可以手动把风险页筛成"只看高等级"，总监也可以把需求池改成按交付日排序——`C.VIEW` 只提供起点，用户的手动调整会通过 `S.setPref()` 持久化，且**按角色分别存储**，互不覆盖。

## 六、快捷新建差异（`C.CREATE`）

`C.CREATE` 共 11 项，每项带 `roles` 数组。**不在角色范围内的项，在首页磁贴、顶栏「＋新建」菜单中一律不渲染，而非灰化**。

| key | 文案 | 总监 | PM |

| `meeting.new` | 会议纪要 | ✅ | ✅ |

| `todo.new` | 待办 | ✅ | ✅ |
| `release.new` | 版本计划 | ✅ | — |
| `roadmap.new` | 规划项 | ✅ | — |
| `review.new` | 经营复盘 | ✅ | — |
| `task.new` | 任务 | — | ✅ |
| `change.new` | 变更申请 | — | ✅ |
| `delivery.new` | 交付物 | — | ✅ |

## 七、数据口径差异（`S.scopeFilter`）

这是"一份数据两种视角"的技术核心。几乎所有实体都带 `projectId` + `lineId` 双字段：

| 角色 | 过滤规则 |
|---|---|
| 总监 | 保留 `lineId === 当前产品线` 的记录；若记录没有 `lineId`，通过 `projectId` 反查其所属产品线 |
| PM | 保留 `projectId === 当前项目` 的记录 |

**两条特例**：

1. **产品线级实体在 PM 口径下自动降级为 `line`**。路线图、OKR、用户反馈、经营复盘这四类没有 `projectId`，PM 看到的是"我这个项目所属产品线"的规划——他需要知道上层意图，只是不能编辑。
2. **全局实体不参与口径过滤**。成员与待办不带口径字段；待办额外按 `role` 隔离，两个角色各看各的。

调用方一律用 `S.xxx()` 取数，`scopeFilter` 在内部生效——**页面代码里没有一处 `if (role === ...)` 的口径判断**，这是"切换角色 = 切换口径"能在 56 个页面上自动生效的原因。

## 八、全局搜索的权限过滤

`S.search()` 跨 8 类实体检索（需求 / 任务 / 版本 / 会议 / 风险 / 反馈 / 项目 / 交付物），返回前有一道过滤：

```js
return out.filter(function (g) { return C.canSee(g.items[0].mod, state.role); });
```

因此**总监搜任务搜不到、PM 搜反馈搜不到**——不可见模块的实体不会通过搜索泄漏。这是权限模型里容易被忽略的一环。

## 九、切换角色时实际发生了什么

```
用户点击角色下拉
  ↓
S.setRole('pm')
  ↓ 写 localStorage['pmw.role']
  ↓ 恢复该角色上次的项目/产品线选择
  ↓ 切换 body[data-role] → CSS 变量整体换色
  ↓ emit('role')
  ↓
06-shell.js 订阅者
  ├─ 重建侧栏（按 C.navFor(role) 过滤分组）
  ├─ 重建顶栏选择器（产品线下拉 ⇄ 项目下拉）
  ├─ 重建「＋新建」菜单（按 C.createFor(role) 过滤）
  └─ Shell.route() 重渲染当前页
       ↓
     当前页若对新角色为 none → 渲染无权限页
     当前页若可见 → 用新角色的 C.VIEW 默认视图重新取数渲染
```

**切角色全程不写库：`S.DB` 里没有任何一条记录被复制、修改或分叉，`DATA.save()` 一次都不会被调用。** 两个角色看的是同一份 `localStorage['pmw.db']`，只是取数口径和权限不同。
